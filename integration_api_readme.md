# Security Encryption API

A stateless REST API that generates AES-128 cryptographic keys on demand.
All communication uses **JWE JSON Serialization** ([RFC 7516](https://www.rfc-editor.org/rfc/rfc7516)) so that key material is never exchanged in plaintext over the wire. Generated keys are returned as **JWK** ([RFC 7517](https://www.rfc-editor.org/rfc/rfc7517)) symmetric key objects, encrypted inside the JWE response.

The service does not store keys. Every request produces a fresh, ephemeral key.

---

## JOSE background

This API relies on two standards from the JOSE (JSON Object Signing and Encryption) family:

| Standard | RFC | Role in this API |
|----------|-----|-----------------|
| JWE JSON Web Encryption | RFC 7516 | Transport envelope for every request and response |
| JWK JSON Web Key | RFC 7517 | Structured representation of the generated AES-128 key (carried inside the JWE) |

Both the request and the response are JWE documents. The shared secret used to protect them is called the **KEK** (Key Encryption Key).

---

## Encryption scheme

```
Algorithm  :  A128KW  (AES Key Wrap, RFC 3394)
Encryption :  A128GCM (AES-128 in Galois/Counter Mode)
KEK size   :  128 bits (16 bytes), base64url-encoded
```

`A128KW` wraps a randomly generated Content Encryption Key (CEK) using the pre-shared KEK.  
`A128GCM` encrypts the payload using the CEK, producing an authentication tag that guarantees integrity.

---

## Endpoints

### `GET /health`

Liveness probe. No authentication required.

**Response `200 application/json`**

```json
{
  "status": "ok",
  "version": "0.1.0"
}
```

---

### `POST /v1/keys`

Generate a new AES-128 key.

- **Request body**: `application/jose+json` — a JWE JSON Serialization containing the key request parameters.
- **Response body**: `application/jose+json` — a JWE JSON Serialization containing the generated JWK.

Both JWEs are encrypted with the pre-shared KEK.

---

## Request format

The HTTP body sent to `POST /v1/keys` is a **JWE JSON Serialization** object (RFC 7516 §7.2).

```json
{
  "protected":     "<base64url(JWE Protected Header)>",
  "encrypted_key": "<base64url(wrapped CEK)>",
  "iv":            "<base64url(96-bit IV)>",
  "ciphertext":    "<base64url(encrypted payload)>",
  "tag":           "<base64url(GCM auth tag)>"
}
```

### JWE envelope fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `protected` | string | yes | base64url-encoded JWE Protected Header. When decoded it must be `{"alg":"A128KW","enc":"A128GCM","cty":"application/json"}`. The server uses this header to select the decryption algorithm. |
| `encrypted_key` | string | yes | base64url-encoded Content Encryption Key (CEK) wrapped with the pre-shared KEK using AES Key Wrap (RFC 3394). The server unwraps this to recover the CEK, then uses the CEK to decrypt `ciphertext`. |
| `iv` | string | yes | base64url-encoded 96-bit (12-byte) Initialization Vector, randomly generated by the client for each request. Reusing an IV with the same key breaks AES-GCM confidentiality. |
| `ciphertext` | string | yes | base64url-encoded AES-128-GCM ciphertext. The plaintext being encrypted is the **key request payload** (see below). |
| `tag` | string | yes | base64url-encoded 128-bit GCM Authentication Tag produced during encryption. The server verifies this tag before accepting the payload; a mismatch causes a `400 decryption_failed` response. |

### Plaintext payload (inside the JWE)

Once the server decrypts the JWE, it expects the plaintext to be a JSON object with the following fields:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `use` | string | no | `"enc"` | Intended use for the requested key. `"enc"` means the key will be used for encryption/decryption; `"sig"` means it will be used for signing/verification (HMAC). This value is echoed into the `use` field of the returned JWK. |
| `kid` | string | no | _(server-generated UUID v4)_ | Client-supplied key identifier. If provided, it is echoed back as the `kid` of the returned JWK, allowing the client to correlate keys with their own records. If omitted, the server assigns a UUID v4 derived from the request. |

**Minimal request payload** (encrypt this JSON inside the JWE):

```json
{
  "use": "enc"
}
```

**Request payload with a client-supplied key ID**:

```json
{
  "use": "enc",
  "kid": "my-service-key-2024-01"
}
```

## Response format

On success (`200`), the server returns a **JWE JSON Serialization** with the same five-field envelope structure as the request. The generated AES-128 key is **never present in cleartext** — it is always inside the encrypted `ciphertext` field.

### JWE envelope (the actual HTTP response body)

```json
{
  "protected":     "<base64url(JWE Protected Header)>",
  "encrypted_key": "<base64url(wrapped CEK)>",
  "iv":            "<base64url(96-bit IV)>",
  "ciphertext":    "<base64url(encrypted JWK)>",
  "tag":           "<base64url(GCM auth tag)>"
}
```

The fields have the same semantics as in the request envelope, with two differences:

| Field | Difference from request |
|-------|------------------------|
| `protected` | Decoded header is `{"alg":"A128KW","enc":"A128GCM","cty":"jwk+json"}` — the `cty` signals that the plaintext is a JWK. |
| `ciphertext` | Encrypts the **JWK** (see below) instead of the key-request parameters. |

All other fields (`encrypted_key`, `iv`, `tag`) follow the same rules as the request — freshly generated per response, verified by the client.

### Plaintext payload (what the client gets after decrypting)

After unwrapping `encrypted_key` with the KEK and decrypting `ciphertext` with the recovered CEK, the plaintext is a **symmetric JWK** (RFC 7517 §6.4):

| Field | Type | Description |
|-------|------|-------------|
| `kty` | string | Key type. Always `"oct"` (octet sequence), indicating a symmetric key. Defined in RFC 7517 §6.1. |
| `k` | string | The generated key material: base64url-encoded 16 random bytes (128 bits). This is the actual AES-128 key. |
| `alg` | string | Intended algorithm. Always `"A128GCM"` — AES-128 in Galois/Counter Mode (RFC 7518 §5.3). |
| `use` | string | Key use, echoed from the request. Either `"enc"` or `"sig"`. Defined in RFC 7517 §4.2. |
| `kid` | string | Key identifier. Echoed from the request `kid` if supplied; otherwise a server-generated UUID v4. Defined in RFC 7517 §4.5. |

**Example — decrypted JWK (not what travels over the wire)**:

```json
{
  "kty": "oct",
  "k":   "GawgguFyGrWKav7AX4VKUg",
  "alg": "A128GCM",
  "use": "enc",
  "kid": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d"
}
```

`k` is the base64url encoding of the 16 random bytes that form the AES-128 key. This JSON object is what lives inside the `ciphertext` field of the JWE response — encrypted and authenticated.

## Error responses

When the request cannot be processed, the server returns plain JSON (the JWE envelope cannot be constructed for error cases).

```json
{
  "error":      "decryption_failed",
  "message":    "JWE decryption failed",
  "request_id": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d"
}
```

| Field | Description |
|-------|-------------|
| `error` | Machine-readable error code (see table below) |
| `message` | Human-readable description |
| `request_id` | UUID v4 identifying the failed request, useful for correlating server logs |

### Error codes

| Code | HTTP status | Cause |
|------|-------------|-------|
| `invalid_request` | 400 | Missing body, malformed JWE structure, or the decrypted payload is not valid JSON |
| `decryption_failed` | 400 | JWE decryption failed — wrong KEK, corrupted ciphertext, or bad authentication tag |
| `internal_error` | 500 | Random number generation or response encryption failed |

---

## Security notes

- The KEK is a **pre-shared secret** between the server and its clients. Rotate it by updating `KEK_VALUE` and restarting the server.
- The server **never logs key material**. Only method, path, status, and latency are logged.
- Every response key is generated from `crypto/rand` — the operating system's CSPRNG.
- Reuse of a JWE IV with the same KEK breaks AES-GCM. The client library must generate a fresh IV per request (the `lestrrat-go/jwx` library does this automatically).
- This version does not use HTTPS. In production, place the server behind a TLS-terminating reverse proxy (nginx, envoy, etc.).
